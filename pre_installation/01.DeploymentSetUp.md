# Assignment Portal on Amazon EKS: Deployment Runbook

Step-by-step guide to deploy the **Assignment Submission Portal** (Flask backend, Nginx frontend, Redis, PostgreSQL) on **Amazon EKS**, exposed through an **AWS Application Load Balancer (ALB)** via the AWS Load Balancer Controller.

Every command below was executed in order. Each step includes the **expected output** so you can verify it before moving on.

## 1. Architecture Overview

```
                       Internet
                          │
                 ┌────────▼────────┐
                 │  AWS ALB (HTTP) │   created by AWS Load Balancer Controller
                 └────────┬────────┘
                          │  target-type: ip
                 ┌────────▼────────┐
                 │ frontend (Nginx)│   Deployment + HPA (2-5 replicas)
                 └────────┬────────┘
                          │
                 ┌────────▼────────┐
                 │ backend (Flask) │   Deployment + HPA (2-5 replicas)
                 └───────┬─┬───────┘
                         │ │
            ┌────────────▼┐ └▼─────────────┐
            │ PostgreSQL  │  │    Redis    │
            │ (EBS gp3 PVC)│  │ (in-memory) │
            └─────────────┘  └─────────────┘
```

| Component | Kubernetes Objects | Service Type |
|-----------|--------------------|--------------|
| PostgreSQL | Deployment, PVC (5Gi, gp3), Service | ClusterIP (5432) |
| Redis | Deployment, Service | ClusterIP (6379) |
| Backend | Deployment, HPA, Service | ClusterIP (5000) |
| Frontend | Deployment, HPA, Service | NodePort (80) |
| Ingress | ALB Ingress | internet-facing |

## 2. Prerequisites

- An **AWS account** with credentials that can manage IAM, EKS, EC2, ECR and CloudFormation
- A Linux **admin host** (EC2 or local) with `curl`, `unzip` and `sudo` access
- `aws` CLI v2, `eksctl` and `kubectl`, installed in [Phase 0](#phase-0-tool-installation-and-cluster-provisioning) (skip any that are already installed)
- An **EKS cluster** with a managed node group (3 nodes were used) and **metrics-server** running, created in Phase 0
- Application images pushed to **Amazon ECR**
- Kubernetes manifests laid out like this:

```
/opt/k8s/assignment-portal-k8s/manifest_files/
├── namespace/namespace.yaml
├── cluster/            # StorageClass (gp3-storage)
├── config/             # ConfigMap + Secret
├── postgres/           # Deployment, PVC, Service
├── redis/              # Deployment, Service
├── backend/            # Deployment, HPA, Service
├── frontend/           # Deployment, HPA, Service
└── ingress/            # ALB Ingress
```

## Phase 0: Tool Installation and Cluster Provisioning

Install the CLI tools and create the EKS cluster. Skip any step you have already completed.

### 0.1 Install eksctl

```bash
curl --silent --location "https://github.com/weaveworks/eksctl/releases/latest/download/eksctl_$(uname -s)_amd64.tar.gz" | tar xz -C /tmp
sudo mv /tmp/eksctl /usr/local/bin
eksctl version
```

**Expected output**

```
0.xxx.0
```

---

### 0.2 Install kubectl

**Download the latest stable release**

```bash
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
```

**Make it executable**

```bash
chmod +x kubectl
```

**Move it to the user binary directory.** This puts it in a standard location for user-installed command-line programs.

```bash
mkdir -p ~/.local/bin
mv ./kubectl ~/.local/bin/kubectl
```

**Add kubectl to your PATH (important).** This adds `~/.local/bin` to your `PATH`, so you can run `kubectl` from any directory by simply typing `kubectl`.

```bash
echo 'export PATH=$PATH:$HOME/.local/bin' >> ~/.bashrc
source ~/.bashrc
```

**Verify the kubectl installation**

```bash
kubectl version
```

**Expected output**

```
Client Version: v1.xx.x
Kustomize Version: v5.x.x
The connection to the server localhost:8080 was refused - did you specify the right host or port?
```

> The "connection refused" line is expected at this point. No cluster is configured yet. Once the cluster exists (0.5), `Server Version` is also shown.

### 0.5 Create the EKS cluster

Three variants were used. Pick **one**. Each sets its own variables, so nothing is hardcoded in the command itself.

| Option | Cluster | Node group | Node type | Nodes | Region | Use |
|--------|---------|------------|-----------|-------|--------|-----|
| A | `my-eks-cluster` | `my-worker-node` | `t2.micro` | 3 | `us-west-2` | Smallest/cheapest test |
| **B** | `my-eks-cluster` | `my-worker-node` | `t2.medium` | 2 | `us-east-1` | **Used for this project** (scaled to 3 nodes in [0.7](#07-scale-the-node-group)) |
| C | `demo` | `demo-node` | `t2.medium` | 1 | `us-east-2` | Single-node demo |

> `t2.micro` supports very few pods per node. Use Option A only for tiny tests, not for this application.

**Option A: `t2.micro`, 3 nodes**

```bash
export CLUSTER_NAME="my-eks-cluster"
export NODEGROUP_NAME="my-worker-node"
export NODE_TYPE="t2.micro"
export NODE_COUNT=3
export AWS_REGION="us-west-2"

eksctl create cluster \
  --name ${CLUSTER_NAME} \
  --nodegroup-name ${NODEGROUP_NAME} \
  --node-type ${NODE_TYPE} \
  --nodes ${NODE_COUNT} \
  --managed \
  --region ${AWS_REGION}
```

**Option B: `t2.medium`, 2 nodes (used for this project)**

```bash
export CLUSTER_NAME="my-eks-cluster"
export NODEGROUP_NAME="my-worker-node"
export NODE_TYPE="t2.medium"
export NODE_COUNT=2
export AWS_REGION="us-east-1"

eksctl create cluster \
  --name ${CLUSTER_NAME} \
  --nodegroup-name ${NODEGROUP_NAME} \
  --node-type ${NODE_TYPE} \
  --nodes ${NODE_COUNT} \
  --managed \
  --region ${AWS_REGION}
```

**Option C: `demo` cluster, 1 node**

```bash
export CLUSTER_NAME="demo"
export NODEGROUP_NAME="demo-node"
export NODE_TYPE="t2.medium"
export NODE_COUNT=1
export AWS_REGION="us-east-2"

  --name ${CLUSTER_NAME} \
  --nodegroup-name ${NODEGROUP_NAME} \
  --node-type ${NODE_TYPE} \
  --nodes ${NODE_COUNT} \
  --managed \
  --region ${AWS_REGION}
```

### 0.6 Reconnect kubectl to the cluster (if there are issues)

If `kubectl` cannot reach the cluster (for example, you are on a new host or the kubeconfig was lost), regenerate the kubeconfig:

```bash
aws eks update-kubeconfig --region ${AWS_REGION} --name ${CLUSTER_NAME}
```

**Expected output**

```
Added new context arn:aws:eks:us-east-1:<ACCOUNT_ID>:cluster/my-eks-cluster to /home/ubuntu/.kube/config
```

### 0.7 Scale the node group

To increase (or decrease) the number of worker nodes:

```bash
export SCALE_NODES=3

eksctl scale nodegroup \
  --cluster ${CLUSTER_NAME} \
  --name ${NODEGROUP_NAME} \
  --nodes ${SCALE_NODES} \
  --region ${AWS_REGION}
```

**Expected output**

```
[ℹ]  scaling nodegroup "my-worker-node" in cluster my-eks-cluster
[ℹ]  initiated scaling of nodegroup
[ℹ]  to see the status of the scaling run `eksctl get nodegroup --cluster my-eks-cluster --region us-east-1 --name my-worker-node`
```

**Verify**

```bash
kubectl get nodes
```

**Expected output:** `SCALE_NODES` nodes in `Ready` state (3 for this project, matching the three nodes shown in `kubectl top nodes` in [4.3](#43-verify-metrics-server)).

### 5.2 ECR Pull Secret

Lets the cluster pull private images from Amazon ECR.

```bash
ECR_PASSWORD=$(aws ecr get-login-password --region ${AWS_REGION})

kubectl create secret docker-registry ecr-registry-secret \
  --docker-server=${ACC_ID}.dkr.ecr.${AWS_REGION}.amazonaws.com \
  --docker-username=AWS \
  --docker-password="${ECR_PASSWORD}" \
  -n ${NAMESPACE}
```

**Expected output**

```
secret/ecr-registry-secret created
```

> ⚠️ ECR authorization tokens expire after **12 hours**. If pods hit `ImagePullBackOff` later, delete and recreate this secret.

## 8. Troubleshooting Notes

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| `ImagePullBackOff` on app pods | ECR token expired (12h) or wrong registry | Recreate `ecr-registry-secret` ([5.2](#52-ecr-pull-secret)) |
| `postgres-pvc` stuck in `Pending` | EBS CSI driver not running, or no pod scheduled yet (`WaitForFirstConsumer`) | Check [4.1](#41-install-the-ebs-csi-driver); the PVC binds once the pod is scheduled |
| Ingress `ADDRESS` is empty | Controller not ready, or IAM/IRSA misconfigured | `kubectl logs -n kube-system deploy/aws-load-balancer-controller` |
| `EntityAlreadyExists` on `create-policy` | Policy already created | Skip the step, or reuse the existing policy ARN |
| HPA shows `<unknown>` targets | metrics-server not running | Check [4.3](#43-verify-metrics-server) |
| Backend restarts once at startup | Backend started before Postgres or Redis was ready | Normal; it settles after one restart |
| `helm install` fails OpenAPI validation | Chart/CRD schema mismatch | The `--disable-openapi-validation` flag is already included |
| `kubectl` cannot connect / wrong cluster | Missing or stale kubeconfig | `aws eks update-kubeconfig` ([0.6](#06-reconnect-kubectl-to-the-cluster-if-there-are-issues)) |
| `kubectl: command not found` | `~/.local/bin` not on `PATH` | Re-run the PATH step in [0.2](#02-install-kubectl) |
| Pods stay `Pending` (insufficient CPU/pods) | Node group too small | Scale nodes ([0.7](#07-scale-the-node-group)) |

## Summary of Deployment Order

0. Install eksctl, kubectl and AWS CLI; create the EKS cluster (Phase 0)
1. EBS CSI driver add-on
2. IAM policy, IRSA service account, Helm, AWS Load Balancer Controller
3. Verify metrics-server
4. Namespace
5. ECR pull secret
6. StorageClass (`gp3-storage`)
7. ConfigMap and Secret
8. PostgreSQL
9. Redis
10. Backend (with HPA)
11. Frontend (with HPA)
12. Ingress (ALB)
13. Verify via the ALB DNS name
