# Monitoring Setup: Prometheus & Grafana on EKS

Installs the `kube-prometheus-stack` Helm chart (Prometheus, Grafana, Alertmanager, kube-state-metrics, node-exporter, and the Prometheus Operator CRDs), exposes Prometheus and Grafana through AWS LoadBalancers, and wires up the `assignment-portal` backend with a ServiceMonitor and alert rules.

> **Do this BEFORE the ArgoCD Application syncs** (see `README-argocd.md`).
> `manifest_files/monitoring/` contains `ServiceMonitor` and `PrometheusRule` objects. These kinds come from the Prometheus Operator CRDs. If the CRDs are missing, ArgoCD fails the whole sync with:
> `failed to discover server resources for group version monitoring.coreos.com/v1`

---

## 1. Prerequisites

| Requirement | Check |
|---|---|
| EKS cluster running, `kubectl` configured | `kubectl get nodes` |
| Helm 3 installed | `helm version` |
| EBS CSI driver and a default/usable StorageClass (Prometheus and Grafana use PVCs) | `kubectl get sc` |
| Cluster can create AWS load balancers (EKS does this out of the box) | |
| metrics-server (needed by the HPAs, not by Prometheus) | `kubectl top nodes` |

Install metrics-server if `kubectl top nodes` fails:

```bash
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
```

---

## 2. Install kube-prometheus-stack

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

helm install monitoring prometheus-community/kube-prometheus-stack \
  -n monitoring --create-namespace
```

> The Helm **release name is `monitoring`**. This matters in step 5: the `release:` label on your ServiceMonitor and PrometheusRule must match this name.

Wait until everything is Running:

```bash
kubectl get pods -n monitoring -w
```

Confirm the CRDs exist (this is what ArgoCD needs):

```bash
kubectl get crd | grep monitoring.coreos.com
```

---

## 3. Expose Prometheus and Grafana via LoadBalancer

Use `helm upgrade` (not `kubectl patch`) so the setting survives future upgrades:

```bash
helm upgrade monitoring prometheus-community/kube-prometheus-stack -n monitoring \
  --reuse-values \
  --set grafana.service.type=LoadBalancer \
  --set prometheus.service.type=LoadBalancer
```

Get the addresses (AWS returns a DNS name, not an IP; `<pending>` for 1-2 minutes is normal):

```bash
kubectl get svc -n monitoring monitoring-grafana monitoring-kube-prometheus-prometheus
```

| Service | URL |
|---|---|
| Grafana | `http://<grafana-elb-dns>` (port 80) |
| Prometheus | `http://<prometheus-elb-dns>:9090` |

> **Use port 9090 for Prometheus.** Port 8080 on the same service is the config-reloader sidecar and only returns `404 page not found`.

### Grafana login

Username: `admin`

```bash
kubectl get secret -n monitoring monitoring-grafana \
  -o jsonpath="{.data.admin-password}" | base64 -d; echo
```

Change the password after the first login.

---

## 4. Restrict access (strongly recommended)

Prometheus has **no authentication**. Anyone who can reach the load balancer can query your metrics. Limit both to your IP:

```bash
helm upgrade monitoring prometheus-community/kube-prometheus-stack -n monitoring \
  --reuse-values \
  --set "grafana.service.loadBalancerSourceRanges={<YOUR_IP>/32}" \
  --set "prometheus.service.loadBalancerSourceRanges={<YOUR_IP>/32}"
```

## 5. Application monitoring manifests

These live in the repo at `manifest_files/monitoring/` and are deployed by ArgoCD:

```
manifest_files/monitoring/
├── backend-servicemonitor.yaml
├── backend-alert.yaml
└── README.md
```

**Critical rule:** both objects must carry `release: monitoring` (the Helm release name). Prometheus only selects ServiceMonitors and PrometheusRules whose `release` label matches. With the wrong label, ArgoCD syncs them happily but Prometheus silently ignores them.

`backend-servicemonitor.yaml`:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: assignment-portal-backend
  namespace: monitoring
  labels:
    release: monitoring          # must match the Helm release name
spec:
  namespaceSelector:
    matchNames:
      - assignment-portal
  selector:
    matchLabels:
      app: backend               # backend Service must have this label
  endpoints:
    - port: http                 # backend Service port must be NAMED "http"
      path: /metrics
      interval: 30s
      scrapeTimeout: 10s
```

`backend-alert.yaml` (header; the five rules are in the repo):

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: assignment-portal-backend-alert
  namespace: monitoring
  labels:
    release: monitoring          # must match the Helm release name
spec:
  groups:
    - name: assignment-portal.rules
      rules:
        # AssignmentPortalBackendDown
        # AssignmentPortalBackendHighCPU
        # AssignmentPortalBackendHighMemory
        # AssignmentPortalBackendPodsRestarting
        # AssignmentPortalBackendUnavailable
```

### Backend requirements for these to work

1. The backend **Service** has label `app: backend` and a port **named** `http`.
2. The backend serves Prometheus metrics at `/metrics` (a Flask exporter in this project).
3. The backend **Deployment** sets `resources.requests` for CPU and memory. The HighCPU and HighMemory alerts divide by the request values, and the HPAs also need CPU requests:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
```

Check the Service:

```bash
kubectl get svc backend-service -n assignment-portal --show-labels
kubectl get svc backend-service -n assignment-portal -o jsonpath='{.spec.ports}'; echo
```

## 6. Verify everything

### 6.1 Scrape target is UP

Open `http://<prometheus-elb-dns>:9090/targets` and find:

```
serviceMonitor/monitoring/assignment-portal-backend
```

It should show **UP**.

### 6.2 Alert rules are loaded

Open `http://<prometheus-elb-dns>:9090/rules` and look for the group **`assignment-portal.rules`** with 5 rules, health **OK**.

### 6.3 Queries return data

"Rule health OK" only means the expressions are valid. Run these in **Query** to confirm data exists:

```promql
kube_deployment_status_replicas_available{namespace="assignment-portal",deployment="backend"}
```
Expected: the number of backend replicas (for example `3`).

```promql
kube_pod_container_resource_requests{namespace="assignment-portal",pod=~"backend-.*",resource="cpu"}
```
Expected: one series per backend pod. If empty, the Deployment has no CPU requests.

### 6.4 Grafana dashboards

Log in to Grafana and open **Dashboards**. The chart ships with ready-made dashboards:

- Kubernetes / Compute Resources / Namespace (Pods): pick `assignment-portal`
- Kubernetes / Compute Resources / Pod
- Node Exporter / Nodes
- Prometheus / Overview

### 6.5 Test that alerts fire (optional)

```bash
kubectl scale deploy backend -n assignment-portal --replicas=0
```

After about a minute `AssignmentPortalBackendDown` goes **Pending**, then **Firing** on the Alerts page. Restore it right away:

```bash
kubectl scale deploy backend -n assignment-portal --replicas=3
```

> ArgoCD `selfHeal` and the HPA will also restore the replica count on their own.

## 7. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Prometheus URL shows `404 page not found` | Used port 8080 | Use port **9090** |
| LoadBalancer stuck on `<pending>` | No AWS LB integration or subnet tags missing | Check `kubectl describe svc`, and that the cluster can create ELBs |
| ArgoCD: `failed to discover server resources for group version monitoring.coreos.com/v1` | CRDs not installed | Complete step 2, then re-sync |
| Rules or target missing in Prometheus though ArgoCD is Synced | `release:` label does not match the Helm release name | Set `release: monitoring`, push to Git |
| Target is `DOWN` | Wrong port name, missing `app: backend` label, or no `/metrics` | See "Backend requirements" in step 5 |
| HPA: `did not receive metrics for targeted pods` | metrics-server missing or no CPU requests | Install metrics-server, add `resources.requests` |
| HighCPU/HighMemory alerts never fire | No resource requests, so the denominator is empty | Add `resources.requests` |
| Grafana pod `Pending` | PVC cannot bind | Check `kubectl get pvc -n monitoring` and the EBS CSI driver |

## 8. Cleanup

```bash
helm uninstall monitoring -n monitoring
kubectl delete namespace monitoring

# Helm does not remove CRDs. Remove them only if you no longer need them:
kubectl get crd | grep monitoring.coreos.com | awk '{print $1}' | xargs kubectl delete crd
```

Delete the LoadBalancers by uninstalling the release (or deleting the services) **before** deleting the cluster, otherwise the ELBs can be left behind and keep billing.
